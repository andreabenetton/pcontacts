# ADR-0024: The app ships a build-time dependency audit snapshot, never a runtime CVE lookup

- **Status:** Accepted (amended 2026-09-22 — ADR-0025 adds an opt-in runtime check on top; the snapshot stays the default and the baseline every runtime result is compared with. Amended the same day: the snapshot is generated from one osv.dev batch query instead of the Dependency-Check report, so regenerating it needs no NVD mirror and no key; Dependency-Check stays the weekly CI second opinion. Amended 2026-10-15: CI's scan is osv.dev only; OWASP Dependency-Check is removed, its CVSS 7.0 gate kept as a HIGH/CRITICAL gate)
- **Date:** 2026-09-22
- **Deciders:** project owner
- **Related:** ADR-0015 (no telemetry, no Google services, no remote configuration), ADR-0001 (license and attribution), ADR-0011 (module boundaries)

## Context

Users of a privacy app want to see what code it ships and whether any of
it carries a known vulnerability. OWASP Dependency-Check already runs in
CI (weekly and on every push) against the release runtime classpath, with
a suppression file that records why a matched CVE does not apply, and the
license report already fails the build on a disallowed license.

None of that is visible in the app. Showing it raises one hard constraint:
ADR-0015 forbids any network call to a host outside `*.proton.me` and any
remote configuration, so the app can never ask NVD, OSV or GitHub for CVE
data at runtime (ADR-0025 later adds one opt-in exception). Whatever the
app shows by default must be fixed at build time, and the F-Droid build
must reproduce it byte for byte, so it cannot be generated from a live
advisory feed during the build either.

## Decision

**The repository commits a dependency audit snapshot, generated by a Gradle
task from the resolved release runtime classpath, the POM-declared
licenses, one osv.dev batch query and the suppression file. The app
packages that file as an asset and renders it: a status indicator next to
the version (green: no known advisory; amber: known advisories assessed
as not applicable, each with its written reason; red: an open one) and a
Dependencies screen listing every artifact with version, license and
advisories with osv.dev links. By default the app performs no lookup at
runtime (ADR-0025 adds the opt-in check); the snapshot states when it was
generated.**

The snapshot is kept honest by two checks:

- `verifyDependencyAudit` fails any build whose resolved classpath differs
  from the snapshot's artifact list (a bump without a regenerated
  snapshot). It runs in the CI unit-test job and needs no network.
- In the CI scan job the same task runs with `-PauditLive=true`: it asks
  osv.dev again and fails when an **open** advisory appears that the
  snapshot does not list (by id or alias), then compares the
  Dependency-Check report as a second opinion. A newly suppressed match
  only logs a warning.

A red status can only ship if the owner regenerates the snapshot with an
open CVE and releases anyway; the build gate makes that a decision, not an
accident. When the shipped snapshot is red, the app posts one notification
per version code pointing at the Dependencies screen.

Links on the Dependencies screen open the osv.dev page through the platform's
external-link mechanism (the user's browser), never an embedded WebView;
the app itself sends nothing.

## Alternatives considered

- **Runtime CVE lookup (NVD or OSV API).** Rejected: a network call to a
  third party from a privacy app, forbidden by ADR-0015, and a dependency
  on that party's availability for a status shown in the UI.
- **Generate the snapshot during the build.** Rejected: advisory data
  changes daily, so the F-Droid build would not reproduce the release APK.
- **Show only the dependency list, no CVE state.** Rejected: the CVE state
  is the part users asked for, and the CI scan already produces it.

## Consequences

- The snapshot is a point-in-time statement. Green means "no known
  advisory against the shipped artifacts when the snapshot was generated".
  An advisory published later is only reflected by the next release, or by
  the opt-in runtime check; the screen says so.
- Regenerating the snapshot becomes a release-checklist step; it needs
  network access to osv.dev and nothing else.
- Suppressions now carry user-visible consequences: every `<suppress>`
  entry's `<notes>` is the reason shown in amber, so it must read as an
  assessment, not a shorthand.
- No new runtime dependency: the asset is parsed with the platform's JSON
  classes.
- Amendment 2026-09-22 (ADR-0025): the coloured indicator described above
  is shown only while the opt-in runtime check is on, and then it reflects
  osv.dev's current findings alone. While the check is off the chip is a
  plain "Dependencies" link and the screen shows the snapshot without
  colours; the snapshot's role is the baseline every runtime result is
  compared with, and the record of what shipped.

## Validation

- Unit tests on the snapshot parser and on the status derivation (clean,
  assessed, open) with a fixture containing each case.
- `verifyDependencyAudit` in CI: a deliberate version bump without a
  regenerated snapshot must fail the unit-test job.
- The weekly scan failing on a new open CVE is the signal that the
  snapshot, and probably a dependency, needs attention.

## Amendment (2026-10-15): CI scans with osv.dev only

OWASP Dependency-Check is removed from the build. It mirrored the NVD
with an API key that GitHub does not give Dependabot's runs, so the scan
failed on every Dependabot pull request whatever it changed, and its
CPE guesses produced matches for other products (the SQLite case). The
`vulnerability-scan` job now runs `verifyDependencyAudit
-PauditLive=true` alone, against osv.dev, which matches exact Maven
coordinates and needs no key.

The gate keeps its strength:

- An open advisory the snapshot does not list still fails, by id or
  alias, as before.
- The NVD scan failed on an unsuppressed finding of CVSS 7.0 or more.
  The live check now fails on any open advisory osv.dev rates HIGH or
  CRITICAL (the GitHub advisory severity of its record), listed in the
  snapshot or not, until it is fixed by a bump or assessed in the
  suppression file.
- The release workflow requires the new job's success on the tagged
  commit, as it required the scan's.

What goes: the comparison with the Dependency-Check report and its SARIF
upload to the Security tab. Trade-off: an advisory recorded only in the
NVD, with no osv.dev record (osv.dev imports the GitHub advisory database,
where Maven advisories are kept), is no longer seen. The suppression file
keeps its name and format; ids and aliases still match.

Nothing below permits less than before, beyond that trade-off.
